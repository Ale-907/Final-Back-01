Ruta de aprendizaje
del proyecto Cine

Comprende las clases, las capas y la base de datos paso a paso.

Guía para un estudiante de segundo semestre · Preparación para explicar y sustentar el proyecto.

Idea central: el proyecto modela un cine y divide el trabajo entre menús, vistas, servicios, repositorios y base de datos. Sigue un dato desde que lo escribe el usuario hasta que se guarda.

Basada en el código de 02_Proyecto_por_capas. Los nombres y rutas se refieren a ese proyecto.

1. Cómo usar esta guía

No tienes que memorizar todas las clases a la vez. Trabaja por etapas, abre en IntelliJ cada archivo indicado y explica en voz alta qué recibe, qué hace y qué entrega.

  1. Primero: comprende qué entidades existen y cómo se relacionan.
  2. Después: sigue un cliente por menú, vista, servicio, repositorio y tabla.
  3. Luego: estudia la venta de un ticket, que combina varias entidades.
  4. Finalmente: practica consultas en phpMyAdmin y responde las preguntas de sustentación.
Objetivo de aprendizaje: al terminar podrás explicar por qué hay clases separadas, qué función cumple cada carpeta y cómo se conserva un dato en MySQL.

2. Qué hace el programa y qué usa

Es una aplicación de consola: muestra menús de texto, recibe opciones con el teclado y permite administrar información del cine. Los datos se guardan mediante JDBC en una base MySQL o MariaDB.

4. Conceptos básicos de Java con ejemplos

Clase y objeto

Una clase es un molde. Cliente describe qué datos y comportamiento tiene un cliente. Un objeto es una instancia concreta, por ejemplo un cliente con cédula 120 y nombre Alejooo. La clase Java se guarda en un archivo .java.

Atributos, constructor y métodos

Los atributos guardan datos del objeto; el constructor permite inicializarlo. Los métodos realizan acciones o dan acceso a sus datos. Los get consultan valores; los set los modifican. private protege el acceso directo y favorece el encapsulamiento.

Interfaz e implementación

Una interfaz es un contrato: declara operaciones disponibles. Una clase que la implementa define cómo se hacen. Por ejemplo, ClienteServiceInterface declara operaciones del cliente y ClienteServiceImpl las desarrolla. ClienteRepositoryPort define operaciones de almacenamiento; ClienteRepositoryDB las realiza con SQL.

Relación entre objetos

Cuando una clase tiene un atributo de otra clase, el objeto puede usarlo. En Ticket hay referencias a Cliente, Pelicula, Sala, Asiento y, opcionalmente, ComboComida. En la versión actual Sala es una única clase con un atributo tipo, no una jerarquía de subclases 2D y 3D.

5. Entidades: por qué existen

Una entidad de dominio representa un concepto importante para el problema del cine. Se mantienen separadas porque cada una tiene datos, funciones y relaciones diferentes. La selección final simplifica el ejercicio y conserva el flujo principal de venta.

ClaseQué representa y por qué conservarla
ClientePersona identificada por cédula y nombre. Permite saber a quién pertenece un ticket. Sus puntos se obtienen a partir de compras registradas.
PeliculaPelícula con ID, título, duración y clasificación. Un ticket necesita identificar qué película se vende.
CineEstablecimiento con ID, nombre y catálogo de películas. Permite agregar y retirar películas de ese catálogo.
SalaSala numerada con capacidad, asientos y tipo 2D o 3D. Unificarla reduce clases duplicadas y mantiene los dos tipos.
AsientoLugar dentro de una sala. Se identifica por número de sala y código; permite controlar la ocupación.
ComboComidaCombo con ID, nombre y precio. Enriquece la compra, pero el ticket puede existir sin combo.
TicketRepresenta la compra y relaciona cliente, película, sala y asiento; incluye precio y combo opcional.

¿Por qué ya no están los empleados? Se decidió retirar Taquillero, Confitero y su clase base Empleado para simplificar el alcance. El ticket actual no registra qué empleado realizó la venta. Esta decisión reduce funciones de gestión de personal; no significa que los empleados no existan en un cine real.

Enumeración: ClasificacionEnum agrupa opciones de clasificación de una película. La carpeta domain/enums reúne este tipo de valores.

6. Cómo se relacionan las entidades

Cliente ───────┐
Pelicula ──────┤
Sala ── Asiento ├── Ticket ── ComboComida (opcional)
               ┘
Cine ── catálogo ── Pelicula
  • Un cliente puede tener varios tickets. Cada ticket guarda la referencia a un cliente.
  • Una película puede aparecer en el catálogo de varios cines y un cine puede tener varias películas. La tabla intermedia es cine_pelicula.
  • Una sala contiene asientos. El código de un asiento se entiende junto al número de su sala.
  • El ticket selecciona una película, una sala y un asiento. El combo puede ser null cuando no se compra.
Límite del modelo: no hay entidad de función con fecha y hora. En esta aplicación cada sala se trata como una única función sin horarios; por ello, el mismo asiento no puede tener dos tickets activos para esa sala.

7. El arranque: App y Config

Paso 1: App.java

El método main es el punto de entrada. Solicita a Config.createUserInterface() una interfaz preparada y llama a su menú de inicio.

Paso 2: configuration/Config.java

Es el lugar donde se arman las piezas. Obtiene la conexión con DataBaseConnection.getInstance().getConnection(); crea mappers y repositorios; crea DatosRelacionados y los servicios; crea las vistas; y finalmente entrega esas vistas a UserInterface.

Connection → ClienteMapper + ClienteRepositoryDB
           → ClienteServiceImpl → ClienteView
           → UserInterface → menú

Este modo de entregar un objeto necesario a otro por el constructor se conoce como inyección de dependencias. Por ejemplo, la vista recibe un servicio; no tiene que construirlo por su cuenta. Las interfaces ayudan a que una capa dependa de un contrato.

8. Recorrido real: crear un cliente

Ejemplo: se desea registrar la cédula 120 y el nombre Alejooo. Sigue estos archivos en orden:

  1. Menú: userinterface/UserInterface.java ofrece la opción de cliente y llama a clienteView.createCliente().
  2. Vista: view/ClienteView.java pide cédula y nombre con FormTypeValidator.stringValidator y llama a service.createCliente(cedula, nombre).
  3. Contrato de entrada: service/inputport/ClienteServiceInterface.java declara la operación que la vista puede solicitar.
  4. Servicio: service/ClienteServiceImpl.java valida que los textos no estén vacíos y que la cédula no exista. Luego construye un objeto Cliente y solicita repository.saveCliente(objeto).
  5. Contrato de salida: service/outputport/ClienteRepositoryPort.java define qué operaciones debe ofrecer un repositorio de clientes.
  6. Repositorio: persistence/repository/ClienteRepositoryDB.java usa la conexión y un PreparedStatement para ejecutar INSERT INTO cliente VALUES (?,?) con los datos.
  7. Base de datos: MySQL/MariaDB guarda una fila en la tabla cliente. Si la operación termina bien, la vista muestra que el registro fue creado.
Al listar: el repositorio ejecuta una consulta; ClienteMapper convierte cada fila del resultado en un objeto Cliente; el servicio devuelve la lista y ClienteView la muestra. La tabla cliente guarda cédula y nombre; los puntos se calculan en la consulta a partir de tickets y combos.

¿Por qué PreparedStatement? La sentencia contiene marcadores ? y los valores se suministran por separado. Así se manejan parámetros sin armar manualmente la consulta con el texto escrito por el usuario.

9. Menús, vistas, servicios y validaciones

UserInterface

Organiza los menús y dirige la opción seleccionada a la vista adecuada. Su trabajo es navegar, no escribir directamente SQL.

view

Solicita datos, muestra resultados y llama al servicio. Hay una vista para cada área principal: clientes, películas, salas, asientos, combos, cines y tickets.

service

Aplica reglas de negocio: por ejemplo, no permitir una cédula repetida o impedir eliminar una sala con tickets asociados. Las reglas están más allá de que el dato sea simplemente un número o un texto.

validations y helpers

FormTypeValidator ayuda a leer tipos desde consola; Validaciones reúne verificaciones usadas por servicios. DatosRelacionados consulta entidades y relaciones necesarias para verificar operaciones; SetClasificacionHelper ayuda con la selección de clasificación.

10. Recorrido de una venta

Antes de crear un ticket, registra un cliente, una película y una sala. La sala crea sus asientos según la capacidad. Un combo es opcional.

  1. En el menú Ticket, la vista solicita identificador, cédula, película, sala, código de asiento, combo y precio.
  2. TicketServiceImpl.createTicket revisa los datos, que el ID no exista y que el asiento no tenga otro ticket registrado.
  3. Usa DatosRelacionados para buscar cliente, película, sala, asiento y, si se eligió, combo. Rechaza relaciones que no existen.
  4. Construye Ticket y llama al repositorio para guardarlo. El valor 0 como ID de combo indica que no se selecciona uno.
  5. TicketRepositoryDB guarda las claves relacionadas y el precio en la tabla ticket. TicketMapper reconstruye el objeto y sus relaciones cuando se consulta.

Total: Ticket.calcularTotal() suma el precio del ticket y, si hay combo, su precio. Ejemplo: ticket 18.000 + combo 28.000 = total 46.000. En la consulta de cliente, los puntos se obtienen sumando la parte entera de cada total dividido entre 1.000; en este ejemplo serían 46 puntos si esa compra permanece registrada.

Protección doble: el servicio valida el asiento y la base tiene una restricción única sobre (sala_numero, asiento_codigo). Las validaciones no hacen atómicas todas las operaciones entre procesos concurrentes: el proyecto está planteado para uso local y una sola instancia.

11. Persistencia, repositorios y mappers

Conexión

DataBaseConnection administra la conexión mediante getInstance() y getConnection(), siguiendo el patrón del profesor. Usa por defecto la base cine_cesde, puerto 3306, usuario root y contraseña vacía. Las variables CINE_DB_URL, CINE_DB_USER y CINE_DB_PASSWORD permiten cambiar esos valores.

Repositorios

Los archivos *RepositoryDB trabajan con la base mediante SQL. Los *RepositoryImpl guardan en memoria para la prueba de capas. La aplicación configurada en Config usa los repositorios DB. JdbcSupport contiene utilidades compartidas por algunos repositorios.

Mappers

RowMapper<T> declara cómo convertir una fila de ResultSet a un objeto de tipo T. Por ejemplo, ClienteMapper construye un cliente a partir de columnas. Los mappers de sala, cine y ticket también ayudan a recuperar relaciones. Config los crea y entrega a los repositorios.

Transacción

Una transacción agrupa operaciones: se confirman con commit si salen bien, o se revierten con rollback si fallan. Se utiliza, por ejemplo, al guardar una sala junto con sus asientos y al guardar el catálogo de un cine.

13. Comparación con el profesor

Ambos proyectos tienen App, Config, dominio, vistas, interfaz, servicios, puertos de entrada y salida, repositorios, conexión y mappers. La diferencia natural es el problema: el profesor modela propietarios y propiedades, mientras que este proyecto modela cine y ventas.

En el código del profesor, PropertyOwnerRepositoryDB recibe conexión y mapper; en el cine, por ejemplo, ClienteRepositoryDB recibe conexión y ClienteMapper. Tu proyecto tiene más entidades y un esquema SQL para sus relaciones. Seguir la estructura no exige que los nombres de las entidades sean iguales ni que cada funcionalidad coincida.

15. Ejercicios prácticos

  1. Localiza en App.java la llamada que crea la interfaz y luego abre ese método en Config.
  2. Busca dónde se comprueba que la cédula de un cliente no esté repetida. Explica qué pasa si ya existe.
  3. En una base de práctica, crea una película y una sala 2D con dos asientos. Consulta las tablas pelicula, sala y asiento.
  4. Crea un ticket sin combo y luego intenta vender el mismo asiento otra vez. Explica el resultado usando el servicio y la restricción SQL.
  5. Abre ClienteMapper: identifica qué columnas lee y qué objeto devuelve. Luego busca dónde se entrega ese mapper al repositorio.

16. Preguntas de sustentación con respuestas breves

¿Por qué separaste el código en capas?
Para que la entrada de datos, las reglas de negocio y el acceso a datos tengan responsabilidades distintas y sea más sencillo entender y modificar cada parte.

¿Qué diferencia hay entre servicio y repositorio?
El servicio valida y coordina reglas del negocio; el repositorio guarda o consulta datos. El repositorio DB utiliza SQL.

¿Para qué sirve un mapper?
Para convertir una fila obtenida desde JDBC en un objeto Java, como un Cliente.

¿Qué hace Config?
Crea y conecta la conexión, mappers, repositorios, servicios, vistas y menú.

¿Por qué una sola Sala?
Porque los tipos comparten la estructura básica; el atributo tipo distingue 2D y 3D y reduce duplicación de clases y menús.

¿Por qué no hay puntos en la tabla cliente?
La consulta del repositorio calcula puntos a partir de los tickets y del precio del combo relacionado.

¿Por qué eliminar empleados?
Para concentrar el alcance en la venta de tickets; el modelo actual no relacionaba los empleados con esa venta.

¿Qué limita el modelo de funciones?
No hay fechas ni horarios: la sala se trata como una única función y se limita a un ticket activo por asiento de esa sala.

¿Qué hacen las interfaces inputport y outputport?
Las primeras declaran operaciones ofrecidas por servicios; las segundas, operaciones que deben proporcionar los repositorios.
